# Android permissions: find, cut, declare

Rules and sources are in [play-facts.md](play-facts.md). This file is the procedure.

## Where permissions come from

The permissions Play sees are the ones in the release build's merged manifest. In an Expo or React Native project they come from four places:

| Source | Where to look | In `android/app/src/main/AndroidManifest.xml` after prebuild? |
|---|---|---|
| App config | `expo.android.permissions` | Yes |
| Config plugins | The `plugins` array; each plugin's README or `app.plugin.js` says what it adds | Yes |
| Expo's own template | Generated by prebuild | Yes |
| Library manifests | `node_modules/<package>/android/src/main/AndroidManifest.xml` | No. Merged at build time |

So the prebuild output is not the whole list. Use the script, then confirm against a real build when you can.

## 1. List them

```
node <this-skill>/scripts/list-permissions.mjs .
```

It reads app config, the app manifest under `android/` if present, and every library manifest in `node_modules`, subtracts `blockedPermissions`, and flags the ones that need a Play declaration or show up in the Data safety form. Library manifests under `src/debug` or test folders are skipped because they do not ship in release builds.

To see what plugins and the template add in an Expo project, generate the native project first:

```
npx expo prebuild --platform android --no-install
```

If `android/` did not exist before, delete it after the script has read it, so the project stays generated from config. Prebuild also rewrites the `"android"` and `"ios"` scripts in `package.json` to `expo run:android` / `expo run:ios`: copy the `scripts` block before running it and restore it after. If `app.config.js/ts` is used, pass `--config` with the output of `npx expo config --json`, saved with `node -e "require('fs').writeFileSync('expo-config.json', require('child_process').execSync('npx expo config --json', { maxBuffer: 1 << 26 }))"` (PowerShell's `>` writes UTF-16, which the script cannot parse). Delete the file afterwards.

Each permission in the output lists its sources. A source that ends in `(maxSdkVersion N)` only requests the permission up to API level N. If every source has a `maxSdkVersion`, the entry also has a top-level `maxSdkVersion`: newer devices never see it.

## 2. Confirm against the release build

The merged manifest of a release build is the ground truth. Any of these works; pass the file to the script with `--manifest <file>` and it treats that file as authoritative:

- An `.aab` from EAS Build: `bundletool dump manifest --bundle app.aab > merged-manifest.xml` (bundletool runs on Java, no Android SDK needed).
- A local release build: the merged `AndroidManifest.xml` under `android/app/build/intermediates/` (the exact folder depends on the Android Gradle Plugin version), or the Merged Manifest tab in Android Studio.

If neither is possible on this machine, say so in `store/data-safety.android.md` and tell the user to check the permission list in Play Console after the first upload.

## 3. Remove what the app does not use

For every permission, find the feature that needs it. If there is none, remove it. Fewer permissions means fewer declarations and fewer Data safety rows.

- **Expo:** add the full name to `android.blockedPermissions`. This also removes permissions a library manifest adds.

  ```json
  {
    "expo": {
      "android": {
        "blockedPermissions": [
          "android.permission.READ_MEDIA_IMAGES",
          "android.permission.READ_MEDIA_VIDEO",
          "android.permission.ACCESS_BACKGROUND_LOCATION"
        ]
      }
    }
  }
  ```

  Check whether the permission's plugin has an option to stop adding it; if it does, use that as well, so the plugin and the block list agree.

- **Bare React Native / native Android:** in `android/app/src/main/AndroidManifest.xml`, with `xmlns:tools="http://schemas.android.com/tools"` on the `<manifest>` element:

  ```xml
  <uses-permission android:name="android.permission.READ_MEDIA_IMAGES" tools:node="remove" />
  ```

Removing a permission a library calls at runtime can crash that code path or make it fail silently. After blocking, exercise the feature that library provides, or confirm the app never calls it.

### Permissions from the Expo template

Prebuild's template can put permissions in the main manifest that no feature of the app uses. One earlier run found `SYSTEM_ALERT_WINDOW` there. Our sources record no Play rule for it; apply the rule above: if no feature needs it, add it to `android.blockedPermissions` and note the decision in the answers file.

## 4. Permissions that need a declaration

Decide for each flagged permission: remove it, replace it, or keep it and prepare the declaration. Record the decision in `store/data-safety.android.md`.

### `READ_MEDIA_IMAGES`, `READ_MEDIA_VIDEO`

Allowed only when the system photo picker cannot support the app's core functionality. An app that lets the user pick a photo to attach or upload is the case the picker covers: block both permissions and confirm the image picker still works on Android 13+. Keep them only if the core feature needs ongoing access to the whole library, and then prepare the declaration. Read https://support.google.com/googleplay/android-developer/answer/14115180 for what qualifies.

### `ACCESS_BACKGROUND_LOCATION`

Keep it only for one core feature that needs location while the app is not in use. If kept, the user needs:

- the declaration in Play Console;
- a demo video of 30 seconds or less showing the prominent in-app disclosure and then the runtime prompt;
- a privacy policy that covers location;
- test credentials if the feature is behind a login.

The disclosure screen must come before the system prompt. What it must say is specified on https://support.google.com/googleplay/android-developer/answer/9799150; read it and build the screen to match, then write the video's shot list into the answers file.

### `USE_EXACT_ALARM` and `SCHEDULE_EXACT_ALARM`

`USE_EXACT_ALARM` is only for alarm, timer and calendar apps, with a declaration. Any other app that needs exact timing uses `SCHEDULE_EXACT_ALARM`, which the user grants, and must handle it not being granted. If the app does not need exact timing (most reminder notifications do not), block both. Source: https://support.google.com/googleplay/android-developer/answer/16558241

### Foreground services

For target 14 and above, each foreground service declares its type and the matching `FOREGROUND_SERVICE_*` permission. In Play Console, App content, give for each type: a description, the user impact if the service is interrupted, a demo video, and the use case. Libraries (audio, location, uploads) can add a service the app never starts; if so, block the permission and confirm the library code path is unused. Source: https://support.google.com/googleplay/android-developer/answer/13392821

### `USE_FULL_SCREEN_INTENT`

Auto-granted only for alarm and calling apps on Android 14+. For anything else, remove it, or keep it only with a fallback for when it is not granted.

### `MANAGE_EXTERNAL_STORAGE`, `QUERY_ALL_PACKAGES`, Accessibility services

Each needs a declaration. Remove unless a core feature cannot work without it. If one stays, read its policy page from https://play.google/developer-content-policy/ (Permissions section) before writing the declaration; our sources do not record what qualifies.

## 5. Permissions that only affect the Data safety form

Camera, microphone, location, contacts, calendar and similar permissions have no declaration in our sources, but each one is a data type to consider in the form. Whether it belongs in the form depends on what happens to the data, not on the permission: read the Data safety help page for how Google defines collection and sharing before deciding. Note the decision and the file that proves it.
